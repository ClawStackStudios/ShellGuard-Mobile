# Master Project Roadmap — [Project Name]

### 🏷️ Work-Driven Versioning Policy: `MAJOR.MINOR.PATCH.REVISION` (`X.Y.Z.N`)
- **No Forced Targets**: Versions evolve naturally and proportionally based on the scope of actual completed work rather than arbitrary future goals.
  - **`MAJOR` (`X.0.0.0`)**: Fundamental structural overhauls, breaking schema migrations, or official 1.0 public launch.
  - **`MINOR` (`X.Y.0.0`)**: Substantial new subsystems or large cohesive feature groups.
  - **`PATCH` (`X.Y.Z.0`)**: Self-contained 2-task milestone deliverables or targeted bug fixes.
  - **`REVISION` (`X.Y.Z.N`)**: Small patches, hotfixes, CI adjustments, or iterative task increments.
  - **`versionCode` (`Build N+1`)**: Monotonically increments (+1) on every Google Play release upload.

---

### 🏛️ Synergistic 2-Task Phase Rule (The Rule of 2)
This roadmap follows a deterministic structure built on the principle: *"Build features around security, not security around features."* Every Phase contains strictly **2 paired tasks**:
1. **Task A: [Functionality]** (Core Logic, Cryptographic Engine, Database DAO, Background Service)
2. **Task B: [UI Component]** (Interactive Compose Screen, State, Gestures, Animations, Edge-to-Edge Styling)

### 🌉 Bridge-Mapping Invariant ("Build the Floor Before the Ceiling")
Never write or schedule feature code without first mapping both sides of the bridge:
- **Data Invariants**: Define the schemas, conflict policies, and zero-knowledge constraints before creating UI screens.
- **Verification Oracles**: Pair each task with deterministic test vectors or binary success criteria that witness the invariant.
